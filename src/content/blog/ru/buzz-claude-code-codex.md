# Buzz: посади Claude Code и Codex в одну комнату

**Смотри видео:** [Claude Code + Codex in One Channel: Buzz Explained](https://youtu.be/NLopx9QY1Bo)

Твой Claude Code крутится в одном терминале. Codex — в другом. Когда одному нужно узнать, к чему только что пришел второй, ты выделяешь текст, переключаешь окно и вставляешь. Интеграционная прослойка тут — это ты, и ты же самое медленное звено.

[Buzz](https://github.com/block/buzz) убирает эту работу. Это самохостящийся воркспейс от Block — Apache-2.0, более 26 000 звезд на GitHub на момент публикации, — где люди и агенты сидят в одних и тех же каналах. Не бот, который пишет в твой чат, а участник: со своей личностью, своим членством в каналах и своим следом в аудит-логе.

## Как это связано, раз ты пришел именно за этим

Кусок, который подключает твоих существующих агентов, — это `buzz-acp`, харнесс из репозитория:

```
Buzz Relay ──WS──→ buzz-acp ──stdio──→ твой агент
                                          │
                                       Buzz CLI
                                    (send_message и прочее)
```

Харнесс слушает упоминания через собаку на релее, дергает твоего агента по протоколу [Agent Client Protocol](https://agentclientprotocol.com/) через стандартный ввод-вывод, а агент отвечает через `buzz-cli` — инструмент вида JSON на входе, JSON на выходе, сделанный для вызова моделью, а не для набора руками.

Подключается что угодно, умеющее ACP поверх stdio. В документации есть два пути через адаптеры и нативная точка входа ACP у Goose:

```bash
# Codex
npm install -g @agentclientprotocol/codex-acp
export OPENAI_API_KEY="sk-..."

# Claude Code (обертка над Claude Agent SDK)
npm install -g @agentclientprotocol/claude-agent-acp
export ANTHROPIC_API_KEY="sk-ant-..."
export BUZZ_ACP_AGENT_COMMAND="claude-agent-acp"

# Goose — нативно, без адаптера
export GOOSE_MODE=auto

buzz-acp   # поднимает агента, коннектится к релею, находит каналы, слушает
```

Одна деталь из документации Buzz, которую лучше знать заранее: если задокументированная конфигурация `codex-acp` пишет `426 Upgrade Required` во время попытки входа в ChatGPT по WebSocket, Buzz называет эту ошибку ожидаемой и нефатальной и рекомендует `OPENAI_API_KEY` как запасной путь.

Смысл именно в протоколе. Ты не покупаешь агента вендора, а направляешь универсальный харнесс на выбранную агентскую среду. Сам Buzz не добавляет отдельную платформенную подписку, но это не означает нулевую общую стоимость: отдельно остаются расходы на модель или API и инфраструктуру для релея. В задокументированном пути Codex нужен `OPENAI_API_KEY`, а адаптер Claude использует `ANTHROPIC_API_KEY`.

## Личность вместо флагов доступа

Вот решение, на котором держится все остальное, и его стоит забрать себе независимо от того, поставишь ты Buzz или нет.

У каждого агента своя пара ключей Nostr. Эта пара **и есть** его личность, а модель событий и подписей задает [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md). Три агента — три пары ключей.

Уровни членства разделены, и это важно. `buzz-admin add-member` регистрирует открытый ключ как **участника релея**. После изменения состава релей публикует подписанный им [снимок списка участников NIP-43](https://github.com/block/buzz/blob/main/NOSTR.md#relay-membership-nip-43) событием kind `13534`. Это список участников релея, а не пара ключей агента и не событие членства в приватном канале. Членство в каналах управляется отдельно, а приватные каналы требуют явного добавления участника.

После этого харнесс находит только те каналы, к которым допущена аутентифицированная личность агента. Документация `buzz-acp` честно отмечает текущий пробел: у релея пока нет REST или событийного API для управления участниками канала. Создание канала через CLI работает, потому что создатель автоматически становится участником.

То есть ограничить агента — это не переключить флаги возможностей в конфиге. Ты добавляешь его в те каналы, которые он должен видеть, ровно как заводишь человека, и все его действия подписаны ключом, который можно проследить. Агент, которому нечего делать в канале про платежи, просто в нем не состоит.

Это заметно другая модель, чем массив разрешений в большинстве агентских харнессов, и это тот же инстинкт, о котором я писал в [Graph Engineering for Multi-Agent AI](https://www.suenot.com/ru/blog/multi-agent-graph-engineering/) и [Agent Harness Architecture](https://www.suenot.com/blog/agent-harness-architecture/): держатся те границы, которые обеспечивает сама среда, а не те, о которых вежливо просит промпт.

## Один лог вместо семи вкладок

Под капотом Buzz — это релей Nostr. Каждое сообщение, реакция, патч, результат CI, шаг воркфлоу и одобрение ревью — подписанное событие в одном логе. Одинаковая форма, одинаковая модель личности, одинаковый аудит-след, написал это человек или процесс. Активность git приезжает событиями NIP-34: патчи, анонсы репозиториев, статусы.

Из этой одинаковости и вырастают три вещи, ради которых им реально пользуются.

**Спроси проект и получи пруфы.** Два часа ночи, ты пишешь: мы такую ошибку уже видели? Агент в канале прочесывает месяцы истории и выкладывает треды, первопричины и починки — ссылками, а не ощущениями. Вопрос и ответ остаются в канале, поэтому следующий человек в два часа ночи найдет сразу оба.

**Ветка становится комнатой.** Открыл фича-ветку — получил канал. Патчи прилетают событиями, CI пишет результаты, агент делает первый проход ревью, коллеги реагируют на то, что их касается, а решение о мердже оказывается в той же комнате, что и доказательства. Канал становится записью того, **почему** этот код существует, — тем контекстом, который обычно испаряется между описанием пул-реквеста и тредом, который никто потом не найдет.

**Релиз, который пишет себя сам.** YAML-воркфлоу срабатывает на тег, агент читает смерженные пул-реквесты из каналов проекта, пишет черновик релиз-нот и выкладывает его на ревью. Воркфлоу уже запускаются сообщением, реакцией, расписанием или вебхуком. Реакция человека выглядит естественным органом управления, но в таблице статуса Buzz формальные гейты одобрения все еще отмечены как незавершенные, поэтому считать этот последний шаг готовым для продакшена пока нельзя.

И вот почему два агента в одном канале — не игрушка: они могут разносить работу друг друга прямо на месте. Claude Code предлагает, Codex проверяет, оба видят один тред, и никто не носит сообщения между вкладками руками. Если у тебя и так каждый день открыты два кодовых агента, это уже достаточная причина.

## С чего начать

Два пути. Быстрый — готовое десктопное приложение (Tauri + React) из [последнего релиза](https://github.com/block/buzz/releases/latest), сборки под macOS, Linux и Windows. По умолчанию цепляется к `ws://localhost:3000`, переопределяется через `BUZZ_RELAY_URL`. Сборка под Windows пока не подписана, так что SmartScreen поругается.

Путь самохостинга требует Docker и Hermit (либо Rust 1.88+, Node 24+, pnpm 10+, `just`):

```bash
git clone https://github.com/block/buzz.git && cd buzz
. ./bin/activate-hermit
just setup
just build

# запусти в отдельных терминалах
just relay   # релей
just dev     # десктопное приложение
```

Релей на `ws://localhost:3000`, приложение поднимается само. Для командного релея без возни с серверами есть деплой в Railway в один клик, для VPS — продакшен-бандл Compose в `deploy/compose/` (Postgres, Redis, MinIO, опционально Caddy с TLS). Корневой `docker-compose.yml` предназначен только для разработки, в прод его тащить не надо.

Для агентов: выставь `BUZZ_PRIVATE_KEY` и дай им дергать `buzz-cli`.

## Что реально готово

Честность про состояние тут важнее рекламы, поэтому вот таблица статусов самого проекта.

**Работает сегодня:** релей, каналы, треды, личные сообщения, канвасы, медиа, поиск, аудит-лог; десктопное приложение; `buzz-cli` и ACP-харнесс для Goose, Codex и Claude Code; YAML-воркфлоу с триггерами по сообщению, реакции, расписанию и вебхуку; git-события NIP-34 и бэкенд для хостинга репозиториев.

**Еще подключают:** мобильные клиенты (iOS и Android, Flutter), гейты одобрения в воркфлоу — инфраструктура есть, склейка не досохла, — и события жизненного цикла звонков.

**Мнения без кода:** репутация через сеть доверия между релеями, пуш-уведомления.

Еще две оговорки, которые стоит знать до того, как заводить туда команду. Приватные каналы требуют явного членства, а REST или событийного API для управления участниками канала у релея пока нет — задокументированный обходной путь в том, чтобы создавать каналы через `create_channel` в CLI, поскольку создатель автоматически становится участником. И правило про ключ — не формальность: секретный ключ нигде не хранится и не восстанавливается. Потерял — потерял личность.

Проект вышел пару месяцев назад и ощущается соответственно. Это плата за то, чтобы прийти достаточно рано и успеть на него повлиять.

## Даже если ты его не поставишь

Три идеи отсюда переносятся на что угодно, что ты строишь:

1. **Давай агентам личности, а не массивы разрешений.** Про членство проще рассуждать, его проще аудировать, и оно вменяемо деградирует: ключа, которому нечего делать в комнате, там просто нет.
2. **Держи разговор и артефакт в одном логе.** Контекст испаряется не потому, что люди ничего не записывают, а потому что записи живут в другой системе, чем код, прогон CI и одобрение.
3. **Пусть реакция человека будет органом управления.** Палец вверх как гейт одобрения не требует обучения и прекрасно аудируется, когда он такое же подписанное событие, как и все остальное.
